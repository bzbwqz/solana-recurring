AGENT-ASSISTED DEPLOYMENT

Let an Agent guide deployment. Keep control of production.

The Deployment Operator Skill plans, preflights, and validates a Portal deployment while secrets and irreversible payment actions remain under human control.

Start on Devnet. Use a separate database, test mint, merchant wallet, subscriber wallet, and webhook secret. Never reuse them on Mainnet.

1. Install the Skill

Clone or download this repository and expose skills/portal-deployment-operator/SKILL.md to your coding Agent. The private source repository contains the same Skill under .github/skills/.

2. Preflight without secrets

The Agent may generate Docker or Bicep templates, inspect image tags, run builds, probe public health endpoints, and run a secret-safe preflight. Enter keys, database URLs, wallet material, and webhook secrets directly in a terminal or cloud secret store. The Agent should report only whether required settings exist.

pnpm deployment:doctor -- --config-file=/opt/solana-recurring/portal.env
pnpm deployment:doctor -- --production \
  --config-file=/opt/solana-recurring/portal.env \
  --health-url=https://portal.example.com/healthz

3. Production confirmation gate

Before production mutation, review image tag/digest, public URL, cluster, mint, merchant public address, receive address, database host, billing state, adapters, and webhook hosts. Explicitly approve the named production target before deployment, billing enablement, Plan publication, webhook replay, or Mainnet activity.

4. Targets

Docker VM: use a fixed image tag/digest and an external mode-600 env file. Azure App Service: use Key Vault references or application settings, WEBSITES_PORT=8080, and Always On. Azure Container Apps: use Key Vault with managed identity, ingress target port 8080, and exactly one replica until distributed worker coordination is verified.

5. Verify

Check /healthz, container revision/image, public URL, database connectivity through application health, webhook reachability, and worker configuration. A healthy container is not a payment-flow acceptance test: complete fixed-payment and recurring subscription checks on Devnet before Mainnet.

Recurring payment boundary: only the Portal worker submits transferSubscription. Odoo, Agents, and downstream services may consume signed events but never become a second scheduler.
